# M3 journal — leaderboard and abuse controls

Date: 2026-09-19  
Status: in progress

This journal records both the implementation and the reasoning behind M3. It is
written so the same design can later be reproduced in another small
Cloudflare-based service.

## Part 1 — durable leaderboard

### Data model

Migration `0004_m3_leaderboard.sql` adds one table:

```sql
leaderboard_entries (
  mode,
  normalized_nickname,
  nickname,
  score,
  game_id,
  completed_at
)
```

The composite primary key `(mode, normalized_nickname)` means one player name
can occupy at most one place in each game mode. A player may therefore have one
satellite result and one metro result, but cannot fill all ten positions by
replaying the same mode. A later result replaces the stored entry only when its
score is higher. For an equal score the earlier completion remains.

The query index follows the exact top-ten order:

1. mode;
2. score descending;
3. completion time ascending;
4. normalized nickname ascending as a deterministic final tie-breaker.

Keeping the query and index order aligned lets D1 read the first ten rows
without sorting the complete table.

### Atomic final round

Accepting a guess now uses `D1Database.batch()` for all related writes:

1. conditionally lock the current `game_rounds` row with
   `WHERE guessed_at IS NULL`;
2. advance or complete `games`, but only when that exact round was written by
   this attempt;
3. on round five, copy the server-owned total into `leaderboard_entries` with an
   upsert.

D1 executes a batch transactionally and in order. If one statement fails, the
whole batch rolls back. After the batch, both conditional updates must report
exactly one changed row. This retains the M1 first-guess lock and prevents a
replayed final request from incrementing the total or creating another ranking
entry.

The browser never submits a round score or game total. The leaderboard insert
selects `total_score` from the completed server-side `games` row.

### Expired-game cleanup

Every newly created game performs one bounded maintenance statement before its
own insert. It removes at most 25 active games whose 24-hour expiry has passed.
`ON DELETE CASCADE` removes their unfinished round rows. Bounded opportunistic
cleanup avoids a separate scheduler for the MVP and prevents a single request
from doing unbounded work.

Completed games are not removed by this cleanup because their result is an
audit source for the ranking. A retention/export policy remains release work in
M4.

### API and browser

`GET /api/leaderboard?mode=satellite|metro` returns:

```json
{
  "mode": "metro",
  "entries": [{ "rank": 1, "nickname": "민수", "score": 24000 }]
}
```

The Worker assigns rank numbers after the indexed query. React renders nickname
values as normal text nodes; markup contained in a nickname is never interpreted
as HTML. The start screen reloads the ranking when the selected mode changes,
and the summary screen shows the ranking for the completed game's mode.
