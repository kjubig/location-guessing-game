# M4 journal — production content and release polish

Status: implementation complete; human clue review and first Cloudflare release
remain owner actions

Last updated: 2026-09-19

This journal explains how the production-size satellite pool was built, what
failed along the way, and how to repeat the process. The goal is not just to
record commands, but to make the boundary between source data, public files,
server-only answers, and the browser explicit.

## 1. Final content model

The reviewed catalogue contains 30 South Korean cities. Each entry has a stable
ID, English and Hangul names, a reference location, a GeoNames record ID, and
three opaque clue IDs. GeoNames is the catalogue source under CC BY 4.0. The
selection intentionally covers different regions rather than merely taking the
30 largest population records.

For every city the pipeline creates three 512 × 512 true-colour WebP images at
Web Mercator zoom 12. The answer is the geographic centre of the exact displayed
tile, not the city reference point. This distinction matters: scoring against a
city centre would punish a correct click on an offset crop.

The resulting release pool is:

- 30 cities;
- 3 clues per city;
- 90 globally unique Web Mercator tiles and public filenames;
- 5.04 MiB of WebP imagery in total;
- 90 server-side answer rows inserted by migration `0005`.

The five older M1 PNG fixtures stay in Git history and Static Assets for
reproducibility, but migration `0005` disables their D1 rows. New games draw
only from the 90 M4 assets.

## 2. Why the pipeline uses Microsoft Planetary Computer

The original plan expected a CDSE account and a local raster stack. During M4,
Microsoft Planetary Computer was verified as the simpler source for this MVP:
its STAC catalogue can be searched anonymously and its Data API can render one
Sentinel-2 item directly as a WebP tile. That removes account credentials and
also avoids installing GDAL, rasterio, Pillow, or `uv` merely for one fixed
transformation.

The Python program therefore uses only the standard library:

1. read the curated city catalogue;
2. convert each reference point to a zoom-12 Web Mercator tile;
3. allocate three nearby tiles that are unique across the entire catalogue;
4. query STAC for Sentinel-2 L2A items from 2024–2025 with less than 15% scene
   cloud cover;
5. select deterministically by cloud cover and item ID;
6. request a 512 px (`@2x`) true-colour WebP from the Data API;
7. reject RIFF files containing EXIF or XMP chunks;
8. hash the source item and tile address into a 20-character opaque filename;
9. write the provenance manifest, city asset IDs, and D1 migration.

Busan and Geoje use an explicit landward candidate order before the common
offset list. A minimum 8 KiB compressed-size heuristic rejects almost uniform
sea/no-data renders. This is a deliberately conservative automated guard, not a
replacement for visual review.

The public browser gets only `/clues/<opaque-id>.webp`. The private-repository
manifest records the item ID, acquisition time, scene cloud cover, tile address,
answer, byte count, and SHA-256 checksum. D1 receives the answer through a SQL
migration; no answer is bundled into the frontend JavaScript or image metadata.

## 3. Rebuilding and refreshing

From the repository root:

```powershell
python -m scripts.geodata.src.golukituki_geodata.build_m4_satellite
pnpm pipeline:test
pnpm db:migrate:local
```

The ordinary command treats the existing manifest as a lock: when city,
variant, and tile match, it reuses the pinned Sentinel item and existing asset.
This makes routine rebuilds fast and repeatable. It also removes only orphaned
20-hex-character WebP files owned by this generator; it never deletes arbitrary
files from `public/clues`.

To deliberately repeat source selection against the current STAC catalogue:

```powershell
python -m scripts.geodata.src.golukituki_geodata.build_m4_satellite --refresh-selection
```

That flag is a content change, not maintenance. Review the manifest diff and
all changed images before committing it. A new selection may produce a different
acquisition date, clouds, snow, haze, water-only crop, or processing artefact.

## 4. Failures that improved the design

### One Sentinel item per city was not safe

The first implementation selected one product for all three offsets. Busan lies
close to a Sentinel/MGRS product boundary: the centre tile existed, but an east
offset was outside that product and returned an HTTP 404. The final pipeline
selects a covering item independently for every tile and records each choice.

### Nearby cities can resolve to the same tile

The first complete run generated 90 manifest rows but only 89 unique paths.
Two close catalogue points selected the same tile and source. D1 correctly
rejected migration `0005` because `round_assets.clue_path` is unique, and the
migration rolled back transactionally. The fix keeps a global set of allocated
`(zoom, x, y)` values and picks the nearest unused offset. A regression test now
requires 90 unique tile coordinates and 90 unique public paths.

These failures show why data constraints and integration tests matter even when
the files themselves look valid.

### Valid files can still be useless clues

A staged-file size review exposed two technically valid but nearly uniform sea
tiles (864 B and 2.4 KiB). Visual inspection confirmed the issue. The generator
now rejects WebP renders below 8 KiB and uses a landward preference for Busan and
Geoje before trying the general offset order. Regeneration removed six stale
files across the two correction passes and produced city/harbour views instead.

## 5. Automated release checks

`pnpm pipeline:test` verifies:

- exactly 30 unique cities and 90 unique clue IDs;
- three assets assigned to every city;
- opaque filenames with no city ID;
- each file's size and SHA-256 against the manifest;
- valid WebP containers without EXIF or XMP;
- globally unique tile addresses and paths;
- fewer than 20,000 public clue files and every file below Cloudflare's 25 MiB
  per-file ceiling;
- a tighter project budget: every M4 WebP below 1 MiB and the whole WebP pool
  at or below 10 MiB.

A fresh D1 migration path leaves five enabled metro assets, five disabled M1
satellite assets, and 90 enabled M4 satellite assets. The working local database
also retains four disabled rows from intermediate M4 runs because the migration
was manually replayed during development. They cannot be selected; a newly
created preview/production database will never contain those draft rows.

The final local HTTP smoke test used Wrangler, the real local D1 binding, and
Cloudflare's official always-pass Turnstile test token. A five-round satellite
game returned five distinct `.webp` clue paths, exposed no pre-guess answer,
completed with a server score, and inserted the result into the satellite
leaderboard. This tests the boundary between generated SQL and runtime code that
unit tests alone do not cover.

Automated checks cannot decide whether every clue is enjoyable or visually
recognisable. Before the first public release, the owner should play/review all
90 images and reject clouds, blank water, processing seams, or misleading crops.
That human curation is intentionally not marked as completed by code.

## 6. Interface and accessibility polish

M4 adds a bilingual sources/licences view, a full-screen map control, and a
keyboard-accessible “select map centre” action. MapLibre already supports
keyboard pan and zoom when its canvas is focused; together these controls let a
player choose a point without a mouse. Escape closes the expanded map. Buttons
keep a 44 px minimum target and visible focus outline, mobile layout collapses
to one column, and system `prefers-reduced-motion` disables UI and result-map
animation.

Per-clue Copernicus/OSM credit stays next to the clue. MapLibre displays Natural
Earth or EOxCloudless attribution inside the map. The dedicated view explains
that the MIT licence covers application code, not third-party data.

## 7. Operations, retention, and remaining owner work

The service stores a nickname, mode, round guesses, scores, and timestamps. It
does not request an account, email, or device identifier. Active games expire
and are removed opportunistically; completed games and leaderboard best scores
are retained for the MVP so rankings survive. If this policy changes, add a
dated migration/cleanup job and update the public privacy wording first.

Before risky production migrations, export D1 outside the repository:

```powershell
pnpm --filter @golukituki/worker exec wrangler d1 export golukituki-production `
  --remote --env production --output C:\secure-backups\golukituki.sql
```

The exported file contains nicknames and guesses. Do not commit it, email it, or
place it in a public cloud folder. Deletion/restore is an owner operation and is
not automated by application deploys.

The remaining release actions require the owner's Cloudflare account or human
judgement:

1. review the final 90 images and run structured scoring playtests;
2. replace placeholder D1 IDs and apply all migrations to preview, then
   production;
3. create preview/production Turnstile widgets and secrets;
4. smoke-test desktop and mobile preview URLs;
5. confirm the app remains non-commercial while the EOxCloudless community
   layer is used, or obtain/replace it with an appropriate commercial source.
