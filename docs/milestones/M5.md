# M5 journal — first public Cloudflare release

Status: in progress; D1, Turnstile and both Workers deployed; GitHub Builds and
end-to-end gameplay checks remain

Last updated: 2026-09-20

M5 turns the locally complete application into an operated web service. It is
deliberately separate from M4: generating production content and deploying that
content are different responsibilities with different failure modes.

## 1. What this milestone delivers

M5 consists of six release operations:

1. create independent `golukituki-production` and `golukituki-preview` D1
   databases in Cloudflare;
2. replace the remote D1 placeholder UUIDs in `apps/worker/wrangler.jsonc`;
3. apply the versioned migrations to preview first and production second;
4. create and configure separate Turnstile widgets for both environments;
5. connect the private GitHub repository to Cloudflare Workers Builds;
6. deploy and smoke-test production and an isolated preview version.

The order used in practice may differ slightly from the list. In particular,
the first Worker deployment gives us the final `workers.dev` hostnames needed
for Turnstile hostname restrictions. When that happens, the first build is
expected to show a controlled “Turnstile not configured” state; it is not
considered the completed release until the widget variables and secrets are
installed and the application is redeployed.

## 2. The service boundary

After M5, one request follows this path:

```text
browser
  -> Cloudflare Worker (API routes)
  -> D1 database (games, rounds and rankings)

browser
  -> Cloudflare Static Assets (React bundle, clues and metadata-free images)

browser -> Turnstile widget -> one-use token
browser -> Worker -> Cloudflare Siteverify (server-side token verification)
```

The browser never connects to D1. The Worker is the trust boundary: it chooses
rounds, keeps correct answers, validates Turnstile, computes scores and writes
leaderboard rows. Static assets and API are deployed together so there is no
separate web server to administer.

## 3. Why preview is a separate service

Production and preview use different Worker names, D1 databases, Turnstile
widgets and rate-limit namespaces. This prevents a test game from entering the
real ranking and lets migrations be exercised against preview before production.

| Concern              | Production              | Preview               |
| -------------------- | ----------------------- | --------------------- |
| Worker               | `golukituki`            | `golukituki-preview`  |
| D1                   | `golukituki-production` | `golukituki-preview`  |
| Wrangler environment | `production`            | `preview`             |
| source branch        | `main`                  | non-production branch |
| Turnstile            | production widget       | preview widget        |

The zero UUID used by the local binding remains unchanged. Wrangler's local D1
emulator stores its data under `.wrangler/` and does not need a real Cloudflare
database identifier.

## 4. D1 creation and migrations

Wrangler first needs OAuth authorization for the Cloudflare account:

```powershell
pnpm --filter @golukituki/worker exec wrangler login
pnpm --filter @golukituki/worker exec wrangler whoami
```

The browser approval grants the local Wrangler CLI access to manage Workers and
D1. It does not put account credentials in this repository. Wrangler stores its
own OAuth token in the user's configuration directory; it must never be copied
into documentation or committed.

Create both remote databases in Western Europe:

```powershell
pnpm --filter @golukituki/worker exec wrangler d1 create golukituki-production --location weur
pnpm --filter @golukituki/worker exec wrangler d1 create golukituki-preview --location weur
```

The returned database UUIDs are identifiers, not passwords. They belong in the
appropriate `env.production` and `env.preview` bindings in `wrangler.jsonc`.

Apply migrations preview-first:

```powershell
pnpm db:migrate:preview
pnpm db:migrate:production
```

This order is a release safety rule. Preview proves that every migration parses,
the final catalogue is usable and the Worker matches the schema before the same
change reaches real user data. Applying a migration is separate from deploying
code; Workers Builds does not run database migrations automatically.

## 5. Turnstile keys and where they belong

Each Turnstile widget provides two values with different security properties:

- `sitekey` is public and is injected into the Vite build as
  `VITE_TURNSTILE_SITE_KEY`;
- `secret key` is confidential and is stored as the Worker secret
  `TURNSTILE_SECRET_KEY`.

The `VITE_` prefix is important: Vite intentionally exposes matching variables
to browser JavaScript. A secret must therefore never use that prefix. Neither
Turnstile secret is committed, printed in logs or copied into this journal.

Production and preview get separate widgets so analytics, allowed hostnames and
key rotation can be handled independently. The production widget permits only
`golukituki.golukituki-worker.workers.dev`. A version preview has the format
`<prefix>-golukituki-preview.golukituki-worker.workers.dev`; because Turnstile
does not accept wildcard characters and these are sibling hostnames, the preview
widget permits their common parent `golukituki-worker.workers.dev`. This broader
frontend scope does not mix environments: only the preview Worker stores the
matching preview secret, while production stores a different secret. Local
development keeps using the official always-pass Cloudflare test pair from the
ignored `.dev.vars` file.

## 6. Workers Builds and CI/CD

GitHub Actions and Workers Builds have different jobs:

- GitHub Actions runs format, lint, type, unit, integration, pipeline and build
  checks; it has no production Cloudflare credential;
- Workers Builds receives a GitHub webhook, checks out the private repository,
  builds the workspace and runs the environment-specific Wrangler deploy;
- Wrangler uploads one Worker containing both the API and `apps/web/dist` static
  assets.

The intended commands are:

```text
Build: corepack pnpm install --frozen-lockfile && corepack pnpm build
Production: corepack pnpm --filter @golukituki/worker deploy:production
Non-production: corepack pnpm --filter @golukituki/worker deploy:preview
```

`main` is the only production branch. Other branches upload a version of the
separate preview Worker and cannot write to production D1.

There is one bootstrap exception. `wrangler versions upload` can only add a
version to an existing Worker, so the very first preview release uses
`wrangler deploy --env preview`. After that one-time creation, non-production
builds return to `wrangler versions upload --env preview` and do not promote the
uploaded version to active traffic.

## 7. Smoke-test protocol

M5 is complete only after checks against deployed URLs, not merely after a green
build log.

For both production and preview:

1. load `/` and confirm that React, CSS, fonts and a clue image are served;
2. request `/api/health` and verify the correct `environment` value;
3. start and finish one satellite game and one metro game;
4. confirm Turnstile succeeds on the expected hostname;
5. confirm a completed result appears only in that environment's leaderboard;
6. inspect browser network responses and verify no answer is sent before a
   guess;
7. refresh an SPA route and confirm the Worker returns `index.html`;
8. verify mobile layout and one desktop browser manually.

The isolation check is especially important: the test nickname written through
preview must not occur in the production leaderboard.

## 8. Rollback and operational recovery

A bad code release is reverted with a new `git revert` commit and the ordinary
`main` deployment pipeline. D1 migrations are not automatically rolled back;
database rollback can destroy data and requires a reviewed corrective migration.

Before any later destructive schema change, export production D1 outside the
repository. The export contains nicknames, guesses and scores and must be
treated as private user data.

If Turnstile blocks every game after a release, check the hostname list, the
public build variable and the Worker secret separately. A correct sitekey with a
missing server secret still fails closed, which is intentional.
